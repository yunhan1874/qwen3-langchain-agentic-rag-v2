# 项目优化审计与实测

日期：2026-10-27。使用真实训练的 Qwen3-1.7B `checkpoint-1082`、现有 2,502 个 Chroma chunk、真实 BGE Embedding 和 Reranker、当前 vLLM 服务。实验改动均在独立审计进程或单次请求内生效，正式页面和配置未改。

**建议优先级：先修引用和评估的可靠性，再加入空过滤预检查和 BM25 倒排；候选数、FP16、聊天模板需要经过独立质量集验证后再切换。** 回答生成占此次三个可回答问题总耗时约 90–95%，单纯优化检索的整体提速空间有限。

## 1. 当前链路耗时

每题测 3 次，排除一个预热请求；采用生产采样参数，并额外固定 seed=0 便于对照。下表为中位数，单位毫秒。各阶段中位数不能严格相加。

| 问题类型 | 全链路 | Dense | BM25 | 精排 | 回答生成 / 改写 | 结果 |
|---|---:|---:|---:|---:|---:|---|
| 血压日常管理 | 903 | 16 | 30 | 37 | 818（回答） | answered |
| 血糖监测 | 905 | 13 | 28 | 36 | 824（回答） | answered |
| 高血压用药注意事项 | 1,595 | 15 | 31 | 35 | 1,508（回答） | answered；达到 256 token 上限 |
| 呼吸道症状记录 | 672 | 12 | 31 | 37 | 583（改写） | abstained |
| 火箭推力 | 674 | 15 | 31 | 46 | 577（改写） | abstained |
| Python 列表排序 | 651 | 14 | 23 | 32 | 576（改写） | abstained |
| 无意义字符 | 654 | 14 | 17 | 41 | 582（改写） | abstained |
| 不存在的显式 source 过滤条件 | 603 | 14 | 3 | 0 | 580（改写） | abstained |

三个领域外问题均拒答；这只是小样例，不是完整的领域外识别准确率。呼吸道问题缺少人工金标，无法据拒答判定它应该被回答。

## 2. 已验证可以保持本次输出一致的提速原型

### BM25 倒排与预计算

当前 BM25 每次遍历所有文档和查询词。实验原型为每个词建立倒排列表，预计算固定语料的 BM25 词项得分；查询时按原查询词顺序累加，保持重复词、浮点运算顺序、过滤及排序规则。

- 24 条真实标题回查，每条测试无过滤、文档类型过滤和无匹配来源过滤：共 72 组，返回 ID、顺序和分数全部逐项一致。
- 另做 480 组合成随机回归，包含重复词、空文本、中文、英文和列表过滤，结果全部精确一致。
- 标题回查的无过滤 BM25 中位耗时从 **72.17ms 降到 22.77ms**，约快 3.17 倍。标题较长，不能将此绝对节省直接套到所有用户短问题。
- 初版倒排原型在无匹配过滤条件时反而更慢（11.33ms 对 1.44ms），随后增加空匹配集合的早返回。应保留这类反例，不能只测试无过滤查询。

### 显式过滤条件预检查

如果本地 chunk 元信息已经证明没有任何文档满足用户的显式硬过滤条件，继续改写查询无法创造符合该条件的文档。实验在这时直接生成相同拒答，避免 Dense、BM25 和 Qwen 改写。该判断不能泛化成“任意低分查询都直接拒答”。

交替运行基准与“倒排 + 显式过滤预检查”原型，每题每种方式 3 次：

| 问题 | 基准 / 秒 | 原型 / 秒 | 本次节省 |
|---|---:|---:|---:|
| 血压管理 | 0.9094 | 0.8832 | 26ms |
| 血糖监测 | 0.9096 | 0.8954 | 14ms |
| 用药注意事项 | 1.5747 | 1.5679 | 7ms |
| 无匹配 source | 0.6041 | 0.0057 | 598ms；未调用 Qwen |

全部 12 对请求的最终证据 ID、顺序、回答 SHA-256 和状态一致。普通问题只获得小幅整体收益；无匹配过滤条件的收益主要来自跳过无效改写。样本少且未锁 GPU 时钟，几毫秒差异不构成普遍延迟承诺。倒排增加初始化和内存成本，本次未做大规模内存压力测试。

## 3. 精排候选数与 FP16

从索引中按固定随机种子抽取 24 条问题标题，以原来源 parent ID 作为回查目标。Dense 和 BM25 各取 12 条，先保留最多 24 条 RRF 并集，再分别精排前 6、12、24 条；每组重复 3 次。使用当前 0.28 阈值，最终最多取 3 条。

| 精排候选上限 | 精排中位耗时 | 候选含原来源 | 最终证据含原来源 |
|---|---:|---:|---:|
| 6 | 20.18ms | 24/24 | 24/24 |
| 12（当前） | 35.46ms | 24/24 | 24/24 |
| 24 | 45.96ms | 24/24 | 24/24 |

这是**标题自回查回归**，不是独立 Recall@K 金标集。标题存在于知识库中，任务容易；不能据此声称候选减半不会降低同义改写、多条件问题或复杂病情问题的召回。

同一批前 12 条候选，将审计进程的 Reranker 从 FP32 转成 FP16：

- 精排中位耗时约 **18.93ms**，对照 FP32 为 35.46ms。
- 最终证据顺序一致 **22/24**，集合一致 **23/24**。
- 对共同进入前五的候选，融合分数最大差约 **0.00124**。

FP16 有速度收益，但已经观察到证据选择变化。该比较仅有小型回归集，且先跑 FP32、再跑 FP16，未做随机轮换；不能当作质量无损开关。应在有人工相关性标注的独立问题集上评估，再决定是否启用和重新校准阈值。

## 4. 不能靠全局缩短回答预算提速

使用完全相同的检索证据和 prompt，交替比较 256 与 128 token 上限，每题各 3 次：

| 问题 | 256 上限：耗时 / 实际 token | 128 上限：耗时 / 实际 token |
|---|---|---|
| 血压管理 | 0.8195 秒 / 136，自然结束 | 0.7709 秒 / 128，被截断 |
| 血糖监测 | 0.8267 秒 / 138，自然结束 | 0.7594 秒 / 128，被截断 |
| 用药注意事项 | 1.4992 秒 / 256，被截断 | 0.7674 秒 / 128，被截断 |

128 上限的 **9/9 请求都达到长度上限**；256 上限也有 3/9 达到上限。更短不等于更完整或质量相同，不建议直接将正式回答上限全局改为 128。

## 5. 改写结构约束与聊天模板

### JSON Schema 格式约束

6 个合成问题，包括医学问题、领域外问题及无意义输入，每种方式各 3 次。复用当前改写 prompt 和 96 token 预算，测试 vLLM 请求级 `structured_outputs.json`。

| 改写方式 | 有效 query + filters JSON | 中位耗时 | 结束情况 |
|---|---:|---:|---|
| 当前原始 completion | 0/18 | 0.5775 秒 | 全部达到 96 上限 |
| JSON Schema 约束 | 18/18 | 2.5240 秒 | 全部自然结束，13–21 token |

此处有效仅指字段和类型可解析，不证明查询语义、医学事实或过滤条件正确。约束成功解决了这批请求的格式问题，但在当前软件栈上明显更慢，不能当作直接提速方案。不同问题反复请求也观察到该开销，不能仅用首次 schema 初始化解释全部差异。

### Qwen 聊天模板与关闭思考前缀

训练脚本使用 ChatML 角色标记；当前生成和改写使用原始文本 completion。补测将原 prompt 完整放入 user 消息，使用检查点 tokenizer 的聊天模板；没有添加新的 system 内容。三个问题各测 2 次。`chat_no_thinking` 同时改变包装并添加 Qwen 的关闭思考前缀，不能将收益拆分为其中单独一项。

| 场景 / 方式 | 中位耗时 | 结果 |
|---|---:|---|
| 回答：raw | 0.8344 秒 | 2/6 被截断；0/6 有原生有效引用 |
| 回答：默认聊天模板 | 1.5015 秒 | 6/6 被截断且思考块未闭合；0/6 有原生有效引用 |
| 回答：聊天模板 + 关闭思考前缀 | 0.7567 秒 | 6/6 自然结束；0/6 有原生有效引用 |
| 改写：raw | 0.5839 秒 | 0/6 有效 JSON |
| 改写：默认聊天模板 | 0.5856 秒 | 0/6 有效 JSON；6/6 思考块未闭合 |
| 改写：聊天模板 + 关闭思考前缀 | 0.1250 秒 | 4/6 有效 JSON，另外 2 次仍触及上限 |

关闭思考前缀有探索价值，但回答并非每题都变快：血糖问题从约 0.826 秒增加到 1.124 秒，输出从 138 增加到 191 token；用药问题则从 256 截断变成 123 token 自然结束。没有医学质量金标，不能用总中位数降低证明答案更好。默认聊天模板也没有解决问题，不能简单地全局套模板。

## 6. 应优先修复的可靠性问题

### 引用格式不等于事实支持

第一轮三个可回答问题共 9 次请求，模型原始回答 **0/9** 主动输出引用编号；目前 `enforce_valid_citations` 会在无引用时补 `[1]`。使用合成的无关回答测试，也能得到 `[1]`。

这说明现有 Citation 能提供结构和来源展示，但不能据此宣称模型做到了逐事实引用。建议保留原始引用状态，区分“检索证据清单”与“模型明确引用”，并逐句校验证据支持；缺少支持的句子应标记、重新生成或拒答。不要把自动补编号当作引用正确率。

### Faithfulness 的词汇代理存在反例

当前函数按答案词语在全部引用 excerpt 中的覆盖率计算，默认阈值 0.35。合成测试：

| 证据与回答关系 | 当前分数 | 预期 |
|---|---:|---|
| 回答将“不应服用”改成“应服用” | 1.0 | 语义冲突，应判不支持 |
| 回答将“10 毫克”改成“100 毫克” | 1.0 | 数值冲突，应判不支持 |
| 无关天文事实对血压记录证据 | 0.0 | 不支持 |
| 完全相同的记录事实 | 1.0 | 支持 |

以上均为合成反例，不是医疗建议。应将当前指标明确命名为词汇支持代理，另建带人工标注的事实支持集，包含否定、剂量、条件、时间和多来源错配；对完整证据做逐声明支持判断。当前评估只读取 180 字 excerpt，也可能漏掉完整上下文后部的支持事实。

### 索引更新不能只校验数量

用隔离的 Chroma mock 跑真实构造函数：先写入一条 `old`，再传入一条不同内容和 ID 的 `new`；数量仍为 1，第二次构造仍保留 `old`。

这复现的是索引更新检查缺失，不是当前生产索引已过期的证据。另外 `chunks.jsonl` 存在时会被复用，也没有核验当前原始语料是否变化。建议存储语料指纹、embedding 模型版本和 chunk 参数清单；变化时生成新版本索引并验证后切换。

### 未闭合思考块会穿过清理函数

合成输入 `<think>synthetic unfinished reasoning` 经当前 `strip_thinking` 清理后仍保留后面的文本。默认聊天模板实验也观察到生成被截断时未闭合的思考块。因此在尝试格式切换前，应修复未闭合块的展示清理，不能只移除标签。

## 验证范围与复现

- 独立进程复用正式 vLLM HTTP 服务，额外加载自己的 BGE 模型；没有另载 Qwen 权重，也没有重建索引。
- 测试结束后 GPU 仅保留原 vLLM 和前端进程；两个服务均返回 HTTP 200。
- 当前 32 项单元测试全部通过；以上可靠性问题属于现有测试未覆盖的反例，不能用单元测试通过证明它们不存在。
- 未进行医学答案人工评分、独立同义查询 Recall@K、在线 A/B 或多人压力测试。
- [逐次机器可读数据](benchmarks/pipeline_audit_20261027.json) 不包含原始医疗段落、原始来源问题或生成回答。

复现脚本使用已安装项目的服务器环境和 README 中的真实路径配置：

```bash
export RAG_LLM_BACKEND=vllm
python scripts/audit_pipeline.py \
  --output output/pipeline_audit/results.json --repeats 3 --lookup-cases 24
python scripts/audit_followups.py \
  --output output/pipeline_audit/followups.json --repeats 3
python scripts/audit_prompt_format.py \
  --output output/pipeline_audit/prompt_format.json
```

倒排、预检查和 FP16 均为审计原型，未接入正式业务代码。下一步可先落地保持本次结果一致的检索优化，再补齐可靠性修复和独立质量回归集；对 FP16、候选数和提示词格式分别做可回退的配置实验。
